# qDesktop — 项目使命说明（Mission）

> 文档版本：v1.1  
> 最后更新：2026-10-08  
> 状态：已确认（定位、MVP 范围、许可证、支持平台、外观设置与托盘交互均经干系人确认）



---

## 1. 使命陈述

**qDesktop 致力于为 Windows 用户提供一个轻量、开源、可自由组织的桌面图标管理工具，把混乱的系统桌面转化为可分层、可收纳、可自动隐藏的个人工作空间。**

一句话版本：*让 Windows 桌面从「一堆散落的图标」变成「按你的逻辑生长的收纳系统」。*

---

## 2. 问题陈述

Windows 原生桌面在图标管理上存在三个结构性缺陷：

| 缺陷    | 具体表现                        | 用户代价                |
| ----- | --------------------------- | ------------------- |
| 无组织能力 | 桌面仅是一个平面容器，图标只能平铺，无法分组、无法嵌套 | 图标数量超过 30 个后即失去可检索性 |
| 无收纳能力 | 无法将图标「收进盒子」，也无法在不需要时隐藏      | 桌面要么全露、要么全藏，没有中间态   |
| 无持久语义 | 图标位置与文件系统耦合，重装/换机后布局丢失      | 组织成本不可复用            |

现有商业方案（如 Stardock Fences）功能完善，但存在付费门槛、闭源不可审计、资源占用偏高等问题；轻量开源替代方案则普遍缺失边缘隐藏与自由层级能力。

---

## 3. 目标用户

**主要用户**：桌面图标数量长期超过 30 个、且愿意为「整洁」投入一次配置成本的 Windows 重度使用者，包括开发者、设计师、内容创作者与办公多任务用户。

**次要用户**：希望获得 Fences 类能力、但偏好开源与本地数据可控的用户。

**典型画像**：同时维护 3 个以上项目文件夹、桌面堆满临时文件与快捷方式，曾尝试用「新建文件夹分类」但最终放弃，因为文件夹需要双击打开、无法一目了然。

---

## 4. 价值主张

1. **栅栏收纳**：以「栅栏」为最小组织单元，将图标分组可视化，避免层层点开文件夹。
2. **自由层级**：栅栏可嵌套、可形成分组树，组织深度由用户决定，而非由程序预设上限。
3. **边缘隐藏**：借鉴 QQ 边缘吸附交互——栅栏可贴边收起，鼠标划入即滑出显示，划出自动隐藏。这是本项目相对轻量开源同类产品的核心差异化能力。
4. **多形态栅栏**：同一套栅栏模型支持三种语义——普通收纳盒（持有图标引用）、便签（持有文本）、文件夹映射（持有真实文件夹的实时视图）。
5. **轻量与可控**：本地优先、数据以明文可读格式存储、无账号、无遥测、开源可审计。

## 5. 范围边界

### 5.1 范围内（In Scope）

| 能力         | 说明                          | MVP |
| ---------- | --------------------------- | --- |
| 栅栏（收纳盒）    | 桌面图标分组容器，可创建、移动、缩放、重命名、删除   | ✅   |
| 自由层级       | 栅栏嵌套 / 分组树，支持任意层级深度         | ✅   |
| 隐藏 / 显示切换  | 栅栏级与整体级的手动显示与隐藏             | ✅   |
| 边缘隐藏       | 栅栏贴屏幕边缘收起，鼠标划入触发滑出，划出自动收起   | ✅   |
| 便签         | 可在桌面创建、编辑、保存的文本便签，作为栅栏的一种类型 | ✅   |
| 文件夹映射      | 栅栏绑定到真实文件夹，内容随文件系统变化实时同步    | ✅   |
| 透明度与颜色设置 | 栅栏背景透明度（0–100% 可调）与背景色、边框色、标题色、文本色均可由用户配置 | ✅ |
| 托盘图标控制 | 单击托盘图标即唤起 / 隐藏全部栅栏 | ✅ |
| 布局持久化      | 栅栏结构、位置、层级、归属关系跨会话保存        | ✅   |
| 多屏与 DPI 适配 | 多显示器环境下的坐标与缩放正确性            | ✅   |
| 支持平台 | Windows 10 1903+ / Windows 11，仅 x64 架构 | ✅ |
| 打包分发       | 可安装的安装包与免安装绿色版              | ✅   |

### 5.2 范围外（Out of Scope，明确不做）

- **不做** macOS / Linux 版本：本项目绑定 Windows 桌面窗口模型（Progman / WorkerW），无跨平台计划。
- **不做** 32 位（x86）与 ARM64 构建：首版仅提供 x64 版本；ARM64 视后续需求再评估，不属于 v1.0 范围。
- **不做** 云同步与账号体系：数据仅存本地，规避账号、隐私与合规成本。
- **不做** 桌面图标之外的资源管理（如任务栏、开始菜单、文件资源管理器增强）。
- **不做** 插件市场与第三方扩展体系：至少 v1.0 前不开放插件 API。
- **不做** 图标美化 / 主题包分发（可支持自定义外观，但不建设内容生态）。
- **不修改** 系统注册表中与桌面图标策略相关的用户设置（如隐藏桌面图标开关），仅读取不篡改。

## 6. 成功标准

### 6.1 功能成功标准（v1.0 验收）

1. 用户可在 5 分钟内完成「创建栅栏 → 把 10 个桌面图标拖入 → 设置边缘隐藏」的完整流程，无需查阅文档。
2. 边缘隐藏的触发延迟 ≤ 150 ms（鼠标进入触发区到栅栏开始动画），滑出动画无明显掉帧（目标 ≥ 55 FPS）。
3. 栅栏结构与归属关系在程序重启、系统重启后 100% 正确恢复。
4. 文件夹映射栅栏在外部新增/删除文件后，视图同步延迟 ≤ 2 s。
5. 空闲状态常驻内存 ≤ 150 MB，CPU 占用（空闲）≤ 1%。
6. 单击托盘图标可在 ≤ 200 ms 内完成全部栅栏的唤起 / 隐藏切换，且托盘图标状态与栅栏实际可见性保持一致。
7. 栅栏背景透明度支持 0–100% 连续调节，背景色、边框色、标题色、文本色均可自定义，调整即时生效并在重启后保持。

### 6.2 项目成功标准

1. 以 **MIT 许可证** 开源发布，仓库包含可构建的完整源码、构建说明与用户文档。
2. 提供安装包与免安装版本各一份；首版不做代码签名，通过分发渠道与文档说明缓解 SmartScreen 告警（详见 tech-stack.md 第 5 节）。
3. 核心模块（数据模型、布局持久化、层级运算）具备单元测试覆盖，行覆盖率 ≥ 60%。

### 6.3 反成功标准（出现即视为方向偏离）

- 为追求功能数量而牺牲「轻量」定位（常驻内存显著超标、启动明显变慢）。
- 因边缘隐藏或桌面层嵌入的技术难点，将核心交互降级为「打开设置面板后手动逐个切换显示」等替代方案。
- 引入必须联网或必须登录才能使用的基础功能。

## 7. 关键约束与风险

| 约束 / 风险          | 说明                                                         | 应对方向                          |
| ---------------- | ---------------------------------------------------------- | ----------------------------- |
| 桌面层技术脆弱性         | 桌面图标窗口层级（Progman / WorkerW）依赖未公开的实现细节，Windows 版本更新可能破坏嵌入方案 | 隔离为独立适配层，保留降级路径（独立置顶窗口模式）     |
| 全局鼠标钩子的稳定性       | 边缘隐藏依赖底层鼠标钩子，钩子超时会被系统摘除                                    | 钩子回调保持极轻量，耗时逻辑投递到独立线程         |
| 与系统「显示桌面图标」设置的交互 | 用户关闭桌面图标后，图标引用会失效                                          | 检测该状态并给出明确提示，而非静默失败           |
| Win10 与 Win11 桌面层结构差异 | 两代系统的 Progman / WorkerW 窗口树结构不同，须做双版本适配 | 阶段 2 在两种系统上分别探测，适配层按系统版本分派 |
| 托盘图标单击语义 | 单击切换与右键菜单需明确区分，且连续单击不能出现状态错乱 | 左键单击绑定唤起/隐藏切换、右键绑定菜单，并做连续单击一致性测试 |
| 单人 / 小规模开发资源     | 阶段必须足够细以支持断续推进                                             | 见 roadmap.md，阶段按 1–3 天可独立验证切分 |

## 8. 使命对齐检查

任何后续功能提案，需通过以下三问：

1. 它是否增强了「把桌面组织成用户自己的结构」这一核心能力？
2. 它是否维持了「轻量、本地、开源」的产品属性？
3. 它是否能在 roadmap 的某个细阶段中被独立交付与验证？

三个问题中任一为「否」，则该提案不进入 v1.0 范围。
